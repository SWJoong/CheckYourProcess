# 설계와 검증: 계획 목록 자동 반영과 병렬 서브 에이전트 표시

상태: 구현됨. 2026-11-12에 Node 테스트와 Claude Code 2.1.322의 band 테스트를 실행하고, 격리한 실제 호스트에서 동기 1개·동시 2개의 서브 에이전트 이벤트를 관찰했다. 설치본 화면 확인과 자동 테스트는 구분한다.

## 목표

사용자가 세션마다 추적을 시작하면 계획 목록과 서브 에이전트 수가 자동 반영되고, 요청이 추가돼도 남은 작업량이 따라 바뀐다.

## 현재 상태

- 진행률은 명시적 `register_tasks` / `update_task` 호출과 계획 도구의 목록으로 갱신된다.
- 훅(`relay.mjs`)은 활동 상태, 계획 목록의 글·상태, 서브 에이전트 ID·수명주기 표지를 로컬 서비스로 보낸다. 서버는 추적에 연결된 세션에만 반영한다.
- 추적은 사용자의 명시적 시작 요청이 있어야 켜진다(`docs/architecture.md`).

## 1. 계획 목록 자동 반영

### 방식

`PostToolUse` 에서 계획 도구(`update_plan`, `TodoWrite`)를 감지해 `tool_input.items` 또는 `tool_input.todos`를 정규화한다. 서버는 해당 세션의 작업 목록과 맞춘다.

- 서버 입력: `tool-end` 이벤트의 `planItems: [{ content, status }]` (최대 100개, 항목당 500자).
- 대응 키: 같은 세션에서 제목이 같고 이번 목록에서 아직 대응하지 않은 작업을 등록 순서대로 재사용한다. 프로젝트 간 병합 기준으로는 쓰지 않는다.
- 맞춤 규칙
  1. 목록에 없던 항목은 새 작업으로 등록한다(총량 증가, 퍼센트 하락).
  2. 목록에서 사라진 항목은 삭제하지 않고 그대로 둔다. 완료 기록이 사라지는 것을 막기 위해서다.
  3. 상태는 `pending` < `in_progress` < `completed` 순서로만 전진한다.
- 완료 규칙: 계획 도구가 `completed` 로 바꾼 것만 완료로 인정한다. `Stop` 이벤트나 서브 에이전트 종료는 완료로 처리하지 않는다(기존 원칙).
- 멱등성: `eventId` 는 `tool_use_id` 기반이라 재전송돼도 중복 등록되지 않는다. 항목 대응은 같은 세션의 직전 목록과 비교하므로 반복 호출에도 안전하다.

### 구현 지점

- `integrations/shared/relay.mjs`: `tool_name` 이 계획 도구이면 `items` 를 추출해 `/api/hook` 으로 전달. 현재 `checkyourprocess` 도구만 제외하는 필터는 유지.
- `src/service.ts`: `hookSchema`가 `planItems`의 필드·길이·상태를 검증한다.
- `src/store.ts`: `handleHook`에서 부모의 `tool-end`에 붙은 계획을 `applyPlan`으로 처리하고 `session_tasks`에 연결한다.
- 테스트: `tests/store.test.ts`, `tests/relay-forward.test.ts`, `tests/relay-debug.test.ts`.

### 결정: 옵트인 (2026-11-12 사용자 결정)

"설정 없이 자동"과 "추적은 명시적 요청 후에만"은 충돌한다. 선택지는 두 가지였다.

- A. 세션마다 한 번 추적 시작을 요청한다(현재 규칙 유지). 시작 이후 목록 반영만 자동이다.
- B. 설정에서 "새 세션 자동 추적"을 켠 사용자에 한해 첫 계획 호출 시 자동으로 추적을 시작한다. 기본값은 끔.

**결정: 이번 구현 범위는 A. B는 후속 과제로 남긴다.**

- A의 시작 수단은 하단 바의 `추적 시작` 버튼(`band.ts` 의 `checkyourprocess:track` 실행) 한 번이다. 별도 설정 화면은 없다. 시작 이후의 계획 목록 반영과 서브 에이전트 표시는 자동이다.
- 설치만으로는 추적하지 않는다는 원칙을 지킨다. 훅은 `start_tracking`으로 연결된 세션에만 작용하며, 연결되지 않은 세션의 계획은 서버에서 무시한다(`handleHook`의 `bound` 검사).
- 후속(B): 설정 항목 "새 세션 자동 추적"(기본 끔)과 첫 계획 호출 시 자동 `start_tracking`. 저장 위치, 설정 화면, 끄는 방법은 그때 설계한다. 기본값을 켬으로 두는 안은 채택하지 않는다.

## 2. 병렬 서브 에이전트 표시

### 현재

- `relay.mjs`는 `SubagentStart/Stop`을 서버로 보낸다.
- `band.ts` 는 `agentId === undefined` 일 때만 중단을 처리한다.
- 서브 에이전트의 도구 이벤트는 부모와 같은 `session_id` 로 들어와 `active_tools` 에 섞인다. 부모가 `Stop` 을 받으면 `active_tools` 가 전부 지워진다.

### 동작

1. 서브 에이전트는 별도 작업 목록이 아니라 부모 작업의 하위 실행으로 본다. 부모 총량과 퍼센트에 직접 더하지 않는다.
2. 실행 중인 서브 에이전트가 N개이면 하단 바에 `서브 N개 실행`을 붙인다. 0개이면 숨기고, 프로젝트 범위에서는 종료하지 않은 세션의 수를 합한다.
3. 서브 에이전트 종료는 부모 작업 완료로 처리하지 않는다. 완료는 부모가 결과를 확인한 뒤 계획 도구로 기록한다.
4. 활동 상태: 서브 에이전트가 실행 중이면 부모의 `Stop` 이후에도 `running` 을 유지한다. 모두 끝나면 `waiting` 으로 바꾼다.
5. 서브 에이전트가 자체 계획 도구를 호출하면(`agent_id`가 붙은 `tool-end`의 `planItems`) 부모 목록에 병합하지 않고 무시한다.
6. 중단·`SessionEnd` 이후 다음 `prompt` 전까지의 늦은 훅은 무시한다. `end_tracking`으로 끝낸 추적은 명시적으로 재개해야 한다.

### 서버 구현

- `hookSchema` 에 선택 필드 `agentId` 추가. `SubagentStart/Stop` 을 `subagent-start/stop` 이벤트로 전달.
- `sessions`와 별도로 `subagent_runs(session_id, agent_id, is_async, handed_back, seen_at)`를 두고 실행·일시 정지·최종 보고를 구분한다.
- `Stop` 처리에서 만료하지 않은 서브 에이전트가 남아 있으면 `running`을 유지한다.

### 실측으로 정해진 사항

- 시작 시점은 `SubagentStart` 로 잡는다. 도구 이벤트의 `agent_id` 로 서브 에이전트와 부모를 구분할 수 있으므로 5번 규칙(서브 에이전트의 계획 호출 무시)도 구현 가능하다.
- 4번 규칙은 실측으로 필요성이 확인됐다. 서브 에이전트 보고가 도착하기 전에 부모의 `stop`이 먼저 오는 경우를 처리한다.
- 기록된 실행이 없는 `SubagentStop`(호스트 내부 보조 작업)은 무시한다.
- 하단 바에는 개수만 표시한다. `agent_type`은 진단 로그에서만 확인한다.

### 설치본 실측 (2026-11-12 11:23, 45초 sleep 서브 에이전트)

- 서버 쪽 표시는 동작한다. 서브 에이전트 실행 중 스냅샷의 `activeAgents` 가 1이었고, 최종 보고 뒤 0으로 돌아왔다.
- **`SubagentStop` 은 "서브 에이전트 작업 종료"가 아니라 "서브 에이전트의 한 턴 종료"다.** 서브 에이전트가 자신의 백그라운드 명령을 기다리느라 멈추면 `SubagentStop` 이 먼저 오고(11:24:11), 명령이 끝나 다시 일어나면 같은 `agent_id` 로 `SubagentStart` 가 다시 온다(11:24:53). 이어서 최종 보고(`SubagentHandback`)와 `SubagentStop` 이 온다.
- 수정 전에는 자기 백그라운드 작업을 기다리는 약 40초 동안 개수가 0으로 표시됐다.
- **수정 (구현함):** 훅 입력에서 두 가지 신호를 찾았다. 부모의 `Agent` 도구 `tool-end` 응답에 `isAsync` 와 `agentId` 가 있어 백그라운드 실행임을 알 수 있고, 서브 에이전트의 최종 보고는 `agent_id` 가 붙은 `SubagentHandback` 도구 이벤트다.
  - 백그라운드로 시작한 서브 에이전트는 `SubagentStop` 이 와도 최종 보고 전까지 "일시 정지"로 보고 개수에 유지한다. 같은 `agent_id` 의 `SubagentStart` 가 다시 오면 같은 실행으로 보고 보고 표시를 다시 연다.
  - 최종 보고 뒤의 `SubagentStop` 에서 비로소 개수에서 뺀다. 백그라운드 실행 표시가 없는(동기) 서브 에이전트는 전과 같이 `SubagentStop` 에서 뺀다.
  - 보고 없이 사라진 서브 에이전트가 영원히 남지 않도록 마지막 활동 후 30분이 지나면 세지 않는다. 그 사이 서브 에이전트의 도구 이벤트가 오면 시간이 갱신된다. 중단·세션 종료 때는 모두 초기화한다.
  - 30분은 임의의 값이다. 동기 서브 에이전트는 아래 추가 실측에서 확인했다.
  - 설치본 재실측에서 찾은 버그: relay 가 서브 에이전트 이벤트 ID 를 `세션:에이전트:이벤트` 로 고정해, 같은 서브 에이전트의 두 번째 `SubagentStop` 이 서버에서 중복으로 버려졌다(개수가 1로 남음). 서브 에이전트 이벤트도 무작위 ID 를 쓰도록 고쳤고 회귀 테스트를 추가했다. 고친 뒤 시작 → 일시 정지(개수 1 유지) → 재시작 → 최종 보고 → 정지(개수 0) 전체 흐름을 설치본에서 확인했다.

### 추가 실측 (2026-11-12 21:00–21:01 KST, Claude Code 2.1.322)

사용자·프로젝트 설정과 MCP 연결을 제외한 임시 세션에서 `Read`만 가능한 probe를 먼저 1개, 이어서 같은 응답에서 2개 실행했다. 각 probe는 임시 표식 파일을 두 번 읽었다. 훅 관찰기는 이벤트 이름·ID·입출력 필드 이름만 기록했고, 사용자 런타임 파일과 기존 서비스는 사용하지 않았다.

| 시각 (KST) | 관찰 |
|---|---|
| 21:00:45.493 → 45.768 | 동기 `Agent` PreToolUse → `SubagentStart` |
| 21:00:52.731 → 53.071 | 동기 `SubagentStop` → 부모 `Agent` PostToolUse |
| 21:00:56.332 / 57.344 | 동시 실행 A / B의 `SubagentStart` |
| 21:01:02.060 / 02.790 / 02.911 / 03.685 | Read 시작 A → 시작 B → 종료 A → 종료 B (실제 겹침) |
| 21:01:05.000 → 05.612 | A의 `SubagentStop` → 부모 A PostToolUse |
| 21:01:05.847 → 06.235 | B의 `SubagentStop` → 부모 B PostToolUse |
| 21:01:09.427 → 09.834 | 부모 `Stop` → `SessionEnd` |

세 동기 `Agent` 응답에는 `agentId`가 있었지만 `isAsync`는 없었다. 이 실험에서는 `SubagentHandback`이 없었으며, 자식 도구 이벤트에만 `agent_id`가 있었다. 관찰한 순서는 보편적인 호스트 보장이 아니다. `tests/store.test.ts`에서 이 순서를 재생해 수 2 → 1 → 0, 부모 Stop 전 running 유지, 미완료 작업 보존을 확인한다.

`SessionEnd` 뒤 늦은 `SubagentStart`를 주입한 회귀 테스트에서 실행 상태가 되살아나는 결함을 발견해 수정했다. 중단·SessionEnd 뒤 다음 prompt 전까지는 시작·도구·정지 이벤트가 상태나 계획을 바꾸지 않는다. 이는 재생 테스트의 확인이며 실제 호스트에서 종료 후 이벤트가 발생하는지는 미확인이다.

### 아직 확인하지 않은 것

- 설치본에서 "부모 `Stop` 이 서브 에이전트 종료보다 먼저 오는" 경우의 활동 상태 유지. 단위 테스트로만 확인했고, 이번 실측에서는 `SubagentStop` 이 `Stop` 보다 먼저 와서 이 경로를 타지 않았다.

- 백그라운드 서브 에이전트 여러 개가 동시에 정지·재시작·보고하는 순서. 위 추가 실측의 동시 실행은 포그라운드였다.
- 백그라운드로 도는 서브 에이전트가 부모 턴이 끝난 뒤에도 이벤트를 보내는지(이번에는 보냄). 부모 세션이 종료된 뒤에도 보내는지는 모른다.
- 서브 에이전트가 계획 도구를 호출할 때 `tool_input` 이 부모와 같은 모양인지(이번 서브 에이전트는 계획 도구를 쓰지 않았다).

추가 TodoWrite 실험(21:05 KST)은 격리한 호스트가 `TodoWrite`를 도구로 인식하지 않아 실패했다. `SubagentStart` → 부모 Agent `PostToolUseFailure` → 부모 Stop → SessionEnd가 기록됐고 자식 Stop은 없었다. 따라서 계획 입력 형태는 여전히 미확인이다. 실패한 시작도 SessionEnd·중단·무활동 만료 전까지 수에 남을 수 있다.

- band 테스트는 `claude plugin test integrations/claude-code`로 12개 통과했다. 한국어·영어의 개수 문구를 terminal·desktop 렌더러에서 검증했지만 실제 설치본 화면의 잘림·배치는 미확인이다.
- 30분 무활동 만료는 실측 근거가 없는 정책이다. 개수 조회에서만 제외하며, 새 이벤트가 없으면 저장된 activity가 자동으로 waiting이 되지는 않는다.
- 계획 도구가 호스트마다 다르다. Claude Code 의 내장 목록, 이 앱의 `update_plan`, Codex 의 목록은 입력 모양이 다를 수 있어 호스트별 어댑터가 필요하다. 이 세션에서는 `update_plan` 만 확인했다.
- 계획 목록의 `content` 가 바뀌면 같은 작업이 새 작업으로 등록될 수 있다(제목 수정). 순서 기반 대응으로 줄일 수 있지만 완전하지 않다.
- 새 prompt 뒤에 이전 턴의 이벤트가 늦게 도착하는 경우에는 턴 ID가 없어 구분할 수 없다.
- 옵트인 B안(설정으로 새 세션 자동 추적)은 후속 과제로 유지한다.
